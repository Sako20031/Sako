# Архитектура

## Почему PWA, а не нативное SwiftUI-приложение

Перед началом был изучен репозиторий `Sako`: в нём уже есть проекты Next.js, развёрнутые на
Vercel, iOS-проектов нет. Среда разработки — Linux без Xcode: нативное приложение здесь
нельзя собрать, подписать и протестировать, а ТЗ требует, чтобы приложение собиралось и было
проверено тестами. Поэтому выбрано **устанавливаемое PWA + отдельный бэкенд**:

- работает на любом iPhone с iOS 16.4+ (полная поддержка Web Worker + OffscreenCanvas);
  на iOS 14–16.3 обработка фото идёт в основном потоке (медленнее, но работает);
- обновляется без App Store;
- весь тяжёлый ИИ на сервере, поэтому возможности телефона почти не важны.

**PWA и нативное приложение не равноценны.** Ограничения PWA на iOS:

| Возможность | PWA на iOS | Нативное SwiftUI |
|---|---|---|
| Камера | через `<input capture>` — системная камера, без ручного управления фокусом и экспозицией | AVFoundation, полный контроль |
| Фоновая работа | нет: при сворачивании JS приостанавливается; анализ продолжается на сервере, результат подхватывается при возврате | BGTaskScheduler |
| Push-уведомления | только iOS 16.4+ и только для установленного на «Домой» PWA (не реализовано) | APNs |
| Офлайн | Service Worker + Cache Storage; iOS может очистить хранилище неустановленного сайта через ~7 дней неактивности | полный контроль |
| Голосовой ввод | Web Speech API в Safari нестабилен; запасной путь — диктовка клавиатуры iOS | Speech framework |
| Секреты | httpOnly-cookie (токен недоступен JS) | Keychain |

Если понадобится нативное приложение: бэкенд и его API не меняются, SwiftUI-клиент
добавляется как ещё один клиент. Для сборки нужны macOS, Xcode 16+, аккаунт Apple Developer
(подпись, TestFlight/App Store или корпоративное распространение).

## Модули

```
frontend (PWA)                                  backend (FastAPI)
─────────────────────────────                   ───────────────────────────────────
Home, ImageAnalysis(ecg|skin|wound),            routers/auth         вход, httpOnly-cookie, роли
Workflow (19 сценариев + неврология),            routers/encounters   вызовы, документация, удаление
Encounter, History, References,                 routers/analyses     загрузка → triage → фоновый ИИ
Medications, Settings, Privacy                  routers/references   протоколы, препараты, офлайн-пакет
lib/triage.ts  ← shared/triage_rules.json →     services/triage      детерминированные опасные признаки
lib/imageCore + workers/image.worker            services/media       проверка файла, качество, копия
lib/api (отмена, дедуп, повторы, backoff)       services/ai/*        провайдеры (Claude | none)
lib/offline (Cache Storage, по запросу)         services/safety      пост-правила над ответом ИИ
public/sw.js (оболочка приложения)              services/report      отчёт A–G
                                                services/documentation  черновик с источниками строк
                                                routers/admin        пользователи, справочник, аудит, хранение
```

## Поток анализа изображения

1. Клиент отмечает опасные признаки → `lib/triage.ts` мгновенно показывает экстренный баннер
   (без сети, без входа).
2. Фото: оригинальный `File` не меняется; worker делает копию (поворот, обрезка, уменьшение
   до 3000 px для ЭКГ / 2048 px для кожи и ран, JPEG q95/q90) и быстрый грубый тест качества.
3. `POST /api/analyses` (multipart, `Idempotency-Key`): сервер **сначала** считает triage,
   затем проверяет файл по содержимому (сигнатура, Pillow verify, лимит пикселей, PDF только
   для ЭКГ), делает свою копию для модели (ЭКГ — PNG без потерь), записывает все преобразования.
   Оригинал сохраняется только если отмечено «Сохранить оригинал». Ответ 202 сразу.
4. Фоновая задача вызывает провайдера. Любой сбой → терминальный статус
   `failed | refused | invalid_output | unavailable | rejected_quality`. Успех возможен только
   с ответом, прошедшим схему Pydantic.
5. `services/safety` применяет правила (см. CLINICAL_SAFETY.md), отчёт A–G собирается
   на чтении; ссылки на источники — только из библиотеки, никогда из ответа модели.
6. Клиент опрашивает результат с растущим интервалом (1→5 с, предел 4 мин), опрос
   отменяется при уходе с экрана. Зависшая задача (перезапуск сервера) помечается `failed`.

Ограничение: фоновые задачи выполняются в процессе веб-сервера (FastAPI BackgroundTasks).
Для нескольких экземпляров и гарантированной доставки нужна очередь (Celery/RQ/Arq + Redis).

## Бюджет производительности (цели, не утверждения)

| Цель | Как обеспечено | Измерено (см. PERFORMANCE.md) |
|---|---|---|
| Стартовый JS ≤ 60 КБ gzip | Preact, код-сплиттинг всех экранов кроме главной, ru в основном пакете, kk/en по запросу; проверка в `npm run build` | 20,3 КБ |
| Главная не ждёт ИИ/сеть | статус ИИ и последние вызовы грузятся после отрисовки | да (e2e) |
| Нет обработки фото в основном потоке | Web Worker + OffscreenCanvas; worker завершается при уходе с экрана | да на iOS 16.4+, нет на старых |
| Нет неограниченных кэшей | офлайн-пакет — один ключ; оболочка — только хэшированные ассеты по факту использования; результаты API не кэшируются | да |
| Длинные списки | пагинация по 20, `<details>` для свёрнутого содержимого | да |
| Без анимаций/теней/blur | плоский CSS | да |
| Предсказуемость при обрыве сети | таймауты, ограниченные повторы GET, без повторов POST, идемпотентный ключ загрузки | да (unit) |
